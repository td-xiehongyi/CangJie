# 项目状态与证据书写约定

适用范围：README、设计/实施计划、交付说明、审查记录和测试结论。更新日期：2026-10-17。

## 状态用词

- **设计目标**：计划实现的行为。不能用现在时暗示已经存在。
- **已实现**：存在对应实现；不等于测试通过、原生可运行或业务效果合格。
- **开发检查通过**：写明具体命令、用例数量、源码基线、操作系统、工具版本以及mock/测试身份；仅证明该范围。
- **正式验收通过**：只有约定真实环境与人员要求已实际完成、有可追溯证据时才能使用。
- **延期/未运行**：没有该次执行结论；不能写成通过、0故障或已完成。
- **受阻**：命令已尝试，但某前置条件阻止后续检查；明确哪些步骤没有进入。
- **已知问题**：区分“静态审查疑点”“已复现”“已修复待复测”“已修复且指定回归通过”。

## 当前状态与历史记录

1. 入口文档开头写检查日期、分支/提交、开发范围与开放问题；“主版本标识”和Git main分开说明。
2. 旧成绩保留原日期和原范围；不把旧Windows/Edge成绩套在后续修改上，不覆盖原日志。
3. “本机”“最近”“当前”“无阻断”“全部完成”须绑定日期、环境和范围；不能将执行者或机器含混地省略。
4. 测试统计标明是否重叠，不将多次重复运行累加成不同用例总数；复现缺陷的断言通过不算功能已修复。
5. 云端工程模型、产品运行模型、确定性测试服务分别写明。测试身份不能表述为实际用户审核。
6. 来源/版本校验必须说明发生时点；“读取时阻断”不写成“任何变化即时停止”，开发打包不写成正式发布。
7. 命令明确从哪个目录、在哪个平台执行，以及是否需要依赖、凭据、外部服务。缺关键条件时不保证可运行。
8. 文件摘要仅证明内容一致；没有可信签名/可信来源校验时不能写成身份认证、恶意篡改不可行或安全证明。
9. 发布代码、合并main、制作开发包、正式发行是四种不同动作；分别记录，不互相替代。
10. 能力结论要写支持范围和拒绝条件。当前工单关闭规则桥不能写成“任意业务自动验证”。

历史证据正文不按新标准改写成绩。存在新发现时，在入口及证据页追加日期化更正并链接新审查记录。

阶段进度/审查原文可移入evidence/archive，日志和机器JSON仍留原位；迁移只调整文档链接，不改日期、成绩和历史决定。入口见[证据索引](evidence/README.md)。已合并删除的旧说明按索引中的固定Git提交回查；冻结JSON及私有测试资源保留原字节，不为修正文档路径改写摘要。


## 工作流与操作说明的写法

1. 固定使用01—11编号、12可选分支；当前导航为01—05、09—12，06—08在05内显示进度，旧链接映射到05。原13并入11，不再出现独立必做13。阶段P1—P6、历史S1—S5与界面步骤是不同编号体系，应注明用途。
2. 每项操作写清前置条件、用户动作、输入、可观察产出、失败/阻断处理。不要用“智能处理”“自动完成”替代具体行为。
3. 区分查看、保存、调用模型和执行测试。跳过页面或复用证据不等于通过检查；导航不能改变执行资格。
4. 说明AI接收方、发送范围、确认时点、输出用途及非AI验证机制。“全部文件”必须限定允许范围、排除项和容量边界。
5. 限额注明单位：KiB=1024字节；字符数、字节数和token不能混写。预算不是费用报价，也不是模型上下文保证。
6. 新业务说明、项目规则、候选、合格方案和运行结果分开表述；不得把“AI发现业务”写成“系统已支持验证”。
7. 可选步骤写明不启用能否结束；复测注明版本失效处理和历史保留方式。
8. 保存说明区分宿主磁盘、浏览器会话、内存与外部服务；明确未保存输入、崩溃恢复和密钥的边界。
9. 功能尚未实现写“未实现”；代码存在但未跑写“未验证”；用户要求暂停写“暂停”。三者不能相互替换。
10. 文档更新不改变历史验收结果；纯文档修改需说明未重跑功能测试。修复过时入口时，保留旧结论的日期和版本范围。

## 提交前核对清单

- README、快速开始、使用说明、实施状态与证据页是否相互一致？
- 所有相对链接是否存在，命令是否写明根目录、环境及前置依赖？
- 当前实现、测试覆盖、设计目标及已知缺口是否能分别定位？
- 是否误将历史通过数、测试桩、类型检查或用例发现当作真实浏览器/原生验收？
- 是否明确暂停项，避免读者误认为已有后台验收任务在执行？
