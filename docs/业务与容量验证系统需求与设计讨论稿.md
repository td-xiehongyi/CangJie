# 面向 AI 辅助开发网站的关键业务与容量验证系统需求与设计讨论稿

版本：0.42  
更新日期：2026-10-13  
状态：需求及最新蓝白四页基准保持；用户已授权并完成 T0—T3，T3独立观察/HTTP验证20/20、完整回归137/137与构建通过；T4—T10尚未开始。实施范围与证据见最终计划2.27及T3验收记录。  
读者：项目发起人及后续设计、开发和评审人员

本项目帮助懂一些开发、缺乏系统测试经验的个人开发者，验证 AI 辅助开发网站的关键业务是否正确，以及在指定环境与负载下是否仍然正确。核心交付是可复查、可重跑的业务与容量证据，用于决定修复、补充验证或发布。

本稿区分已确认需求、拟议机制与候选扩展。只有明确标为已确认的内容构成当前需求共识；首版保留接入复用、业务检查、可重跑验证包和目标负载验证，并将候选模板生成、独立验证、审核发布及跨项目复用纳入主线，外围范围按 R30 压缩。用户已接受创新原型方向、仓颉核心加 TypeScript 工具层及本地网页形态，并接受首批 Node.js、Express、HTTP/JSON、SQLite 的支持范围。具体接口、依赖兼容性、实现规模与性能指标仍待确定。

### 必须保留的核心原则

> 支持多种网站，必须积累可复用的接入、实验、判定与复测能力；新项目接入后，应复用并扩展已有能力，而不是每次重新组织提示词、临时生成测试。

用户明确认同该原则，并要求长期记录。后续功能取舍需要检查：它是否降低新项目接入成本，是否提高验证可靠性，是否形成下次仍能使用的成果。

如果某项能力仅需要一组提示词和调用步骤，Skill 可能是合适的实现方式。独立软件的价值需要体现在执行、状态保存、证据管理和复用上。Skill 也可以作为软件能力的调用入口，二者并不互斥。

## 用户问题与项目目标

目标用户可能已经能够运行网站、通过现有测试，却无法判断测试覆盖了哪些重要业务要求，也不知道网站在预期使用方式下能否正常工作。

本项目需要帮助用户获得四类结果：

1. 明确哪些关键业务缺少可信证据，以及本轮优先验证什么。
2. 获取可以复现的问题，说明实际行为违反了哪条已确认规则。
3. 获取绑定版本、环境、数据和负载条件的验证结论，并知道未覆盖范围。
4. 修复后使用已保存规则复测，确认问题是否消失，以及前后结果是否可比。

不把代码能够编译、服务可以启动、HTTP 返回成功或测试数量多，单独作为业务正确或可以上线的充分依据。

“比强模型更有价值”是需要验证的假设，不能作为既成事实。带工具的通用 AI 也能设计、执行和复核测试。本项目应在相同模型与资源条件下证明可靠性、接入成本或持续复测方面的实际增益，而非宣称通用 AI 无法完成同类任务。

## 可信输出的机制与待细化事项

已确认的行为边界见 R01 至 R52；以下进一步说明设计依据。具体证据格式、模板对照与实现细节仍待细化。

### 区分规则与实现现状

业务正确性来自用户确认的要求及适用依据。源码描述的是当前实现，不能自动成为正确标准。系统应保留已确认规则、当前观察、模型推测和未决问题之间的区别。

例如，“同一次提交重试只产生一张工单”应先确认为业务要求；代码当前创建了两张工单，不能反过来证明两张就是正确行为。

### 让结论受证据约束

拟议的通过条件至少包含：规则、版本、环境、执行记录、结果证据、判定方法与验证范围。未执行不能显示已验证；查询失败不能解释为没有错误；疑似根因不能当成已证实原因。

AI 可以探索、协助接入、解释结果，并选择、配置和组合已验证模板；没有适用模板时进入候选生成与验证流程，验证不足或原语不支持仍须报告缺口。可明确计算的判定由检查程序执行。规则未定时只记录授权范围内的实际行为，不判通过或失败。

判定程序本身也可能错误。系统不能因为脚本能运行，就认为检查有效。

### 验证检查是否能够检错

关键检查应考虑逻辑与完整执行链两层验证：

- 逻辑层：已知正确与错误的输入，应分别得到相应结果。
- 执行层：在可控副本或独立缺陷样例中，确认测试能够取得目标证据，并因对应业务错误失败。
- 取证层：使用本轮标识关联操作与结果，避免历史数据、分页遗漏、错误账号及查询异常造成误判。
- 修改规则：执行过程中不得静默放宽已确认条件；必要修改应保留原因与版本。

首版在开发者审核的受控参考服务和缺陷样例上验证候选，不自动修改用户源码注入故障。具体对照集和复位步骤在实施任务中验证；编译、启动失败或查询超时不能冒充检出业务缺陷。

这些机制不能证明不存在所有缺陷；它们支持的是特定范围内的验证结论。

### 将业务正确性纳入容量结论

已确认压缩后的首版只验证目标负载，按 R10、R11 处理业务失败与停止，停止后结算在途操作。目标通过后结束；更高负载探索与降载恢复观察后移。预期未知时沿用 R09 先引导并确认。目标数值、时长、阈值、窗口与资源预算仍需确定；每分钟 60 次报名、持续 10 分钟仅为说明，不是默认配置。

负载方案需要说明操作比例、身份与热点分布、数据规模、到达方式、持续时间、完成时限和失败条件。注册人数、在线人数、虚拟用户数、并发请求数和业务完成量不能混用。

在提交工单的示例中，应关联独立业务操作、接受情况与最终有效记录，区分正常拒绝、重试、异步处理中和真正失败。速度与业务条件共同满足要求，才记为该级负载通过。

报告应区分已测通过、已测未通过与尚未测量范围，不能将单次通过点描述为最大容量。压测工具与被测网站共用本机资源时，需要说明干扰；本机结果不能直接代表线上部署，也不能脱离使用方式换算最大人数。

### 已确认的首批被测网站范围

开发本系统所用的语言与系统支持测试的网站语言分开定义。首批深度支持 Node.js 24 下的 TypeScript 或 JavaScript、Express 5、HTTP/JSON 接口和 SQLite 本地数据；浏览器入口不要求被测网站必须使用 React。

Node.js 是服务器端 JavaScript 运行环境，不是某一种业务网站，也不等于 Express。NestJS、Next.js 等有不同的启动和框架约定；确认 Node.js 生态不等于同时承诺全部框架的深度适配。其他后端语言的网站若提供可访问的 HTTP 接口或页面，也可能复用外部行为实验，但启动、源码识别、认证、数据准备与结果取证能力必须分别验证。

SQLite 选择服务于易启动、易复制和单人交付，不代表它适合所有负载。SQLite 每个数据库文件同时只允许一个写入者，容量报告须保留这一环境条件，不将结果外推到 PostgreSQL 或多实例部署。未来扩展数据库时，重新运行相关实验，不直接继承旧容量结论。

4. 结果查询失败、启动失败或测试脚本失效时，不误报为业务通过。
5. 重试和多人操作后能够关联最终记录，判断相应业务性质。
6. 在目标负载下同时评估性能与业务结果，区分目标未达标、证据不足和压测端限制。
7. 修复后按相同规则复测，条件发生变化时明确提示。
8. 不支持的新项目给出具体适配缺口，不生成全面通过报告。
9. 没有模板时生成候选，正对照通过、对应负对照因正确断言失败、查询失败为未知；审核后发布并在第二网站复用。

这些场景用于继续收敛验收合同，尚无执行结果。
