实施入口：[源码业务分析分阶段计划](../plans/2026-10-14-code-grounded-business-discovery.md)。计划中的S1—S5细化本稿A—D依赖顺序；预算与接口的开发实现状态以该计划及对应测试证据为准；本稿的设计目标不能单独证明能力已实现或正式验收通过。

## 1 目标与当前缺口

用户希望导入项目后，系统能根据实际源码分析业务、推荐项目特有的检查，而不主要依赖几种固定规则。此次优先整理源码业务分析，命名审查后移；原业务执行与可信证据机制继续保留。

本设计启动时有三层限制：默认AI文件范围只有verification.json；AI生成的pendingRules显示为待确认建议，但未成为动态项目规则进入执行链；实际执行使用已有规则目录，操作能力固定为create/query/update等。扩大文件读取范围只能改善输入，不能单独解除后两项限制。

verification.json主要描述启动、认证、接口及字段映射，不能代表完整业务实现。目标设计中它降为运行适配配置：可用于核对分析结果及执行，但不再是源码分析的必需前提或唯一材料。

“理解项目”的可验收含义是：识别主要业务对象、角色、操作与状态关系；每个结论能回到源码；列出未读范围和不确定项；能提出与项目实现相关且有明确预期的检查。不会以“读取了很多文件”或模型自报置信度证明全面理解。

## 2 推荐路线

| 路线 | 效果 | 选择 |
| --- | --- | --- |
| 一次发送整个仓库 | 上下文容易超限，重要调用关系可能淹没，仍缺覆盖和证据管理 | 不采用为默认方案 |
| 用户手工选若干文件 | 实现简单，但用户需要预先知道业务分布，容易漏服务或权限逻辑 | 保留为高级补充 |
| 本地建立索引，AI按业务链读取相关源码 | 可控制发送范围、逐步补齐关联代码、形成证据和覆盖记录 | 推荐 |

初期聚焦当前主要支持的JavaScript/TypeScript网站源码，覆盖TSX/JSX页面与服务代码；跨语言、复杂动态路由和框架先标明识别限制。源码分析的语言支持与网站执行支持分别显示。不能启动网站，也可以分析源码；能分析源码，不等于已经能运行该网站的检查。

## 3 分阶段读取源码

### 3.1 本地索引

选择项目后，本地程序先收集允许范围内的目录、文件类型、内容指纹、入口、路由、导出符号与导入关系；解析失败时保留文本搜索入口和限制说明。忽略依赖、构建输出、版本库及秘密配置。用文件和代码片段索引起步，不先引入向量数据库。

这个阶段不自动把完整正文发送给远端模型。索引能建立跨文件导航，但符号引用不能直接证明运行时调用必然发生。

### 3.2 确认分析范围

界面展示将提供给模型的目录摘要、允许读取的源码目录、排除目录、模型服务及预算。用户确认一次本轮范围，系统在范围内逐次选取相关片段；需要访问新目录时再扩展确认，不对每个已授权文件重复询问。

UI需说明“目录摘要也会发送”，以及实际正文将按需读取。文件名与内容的过滤保留，过滤不能承诺识别所有秘密。密钥、数据库文件和工具自身私有评估答案不进入模型上下文。

被测项目已有测试可作为可选业务材料，但必须与工具的独立验证资源分开管理。测试表达的是已有作者的预期，不能自动视为可信答案。若使用项目测试作分析输入，后续不能再把同一测试称为生成时未见的独立评估。

### 3.3 按业务链扩展读取

先读项目说明、依赖和入口，形成业务入口候选；随后沿“页面或接口 → 处理函数 → 服务逻辑 → 数据模型与约束 → 权限或状态判断”扩展。

模型通过受限的搜索、查看符号、读取片段和查引用能力请求补充材料，宿主负责范围、片段大小、轮次、累计字节与成本限制。源码中的文字只能作为分析材料，不得改变读取授权或触发命令执行。

每次返回片段携带文件路径、内容指纹、行区间和片段ID。报告引用由系统校验属于实际读取片段；用户可展开原文，避免模型凭空生成文件位置。

### 3.4 保存覆盖和停止理由

分别记录“已索引”“正文已读取”“仅模型推断”“尚未追踪”的范围，以及过滤、截断、解析失败、动态调用未解析等缺口。到达预算后保存部分结果和未完成项，不显示全项目分析完成。

设计要求：分析期间源码变化时，不把不同版本片段拼成同一结论，应停止受影响分析并建立新快照。当前实现逐轮核验旧快照文件；公开读取及确认入口重建选中范围并使过期结果失效。已知缺口：运行期间新加入范围内的文件不会被旧文件遍历发现，可能继续调用并保存completed，直至公开读取才标stale。该问题已复现、尚未修复；不能声称所有源码变化都会即时停止。修复后仍须补相应开发回归及原生验收。

## 4 AI应输出什么

### 4.1 业务概览

输出业务对象、角色、主要操作、状态变化、关键约束和外部依赖。概览允许列出多条业务，用户每次选择一条深入；沿用“一次运行一条主业务流程”的执行边界。

每条结论必须区分来源：

| 来源类别 | 示例 | 含义 |
| --- | --- | --- |
| 代码事实 | 服务函数只在订单处于pending时执行取消 | 当前实现的可定位行为 |
| 文档或项目测试中的预期 | 文档写“取消未支付订单后释放库存” | 可能代表需求，但需核对是否过期 |
| AI风险推断 | 取消重试可能导致重复释放库存 | 值得检查的假设，还不是已发现缺陷 |
| 用户确认的预期 | 同一订单重复取消最多释放一次库存 | 可以作为业务检查的目标规则 |

不能仅把现有实现转写成预期。若实现漏了权限检查，不能据此生成“任何用户均可取消订单”的正确性规则。存在代码、文档冲突时列出冲突，仅对影响判定的关键问题询问用户；无需要求用户逐文件确认。

### 4.2 检查建议卡片

每项建议包括：业务名称、为什么值得检查、代码依据、候选预期、操作前提、如何观察结果、待确认事项、优先级理由、执行准备状态。说明来自静态分析，不写“已验证存在漏洞”。

示例为假设的商城项目，并非当前样例已有能力：

> 检查：取消订单后库存是否恢复且只恢复一次。  
> 依据：取消入口、库存释放服务、订单状态字段的实际读取片段。  
> 风险：重试可能重复释放；当前源码尚不能证明所有路径有防重保护。  
> 请确认：未支付订单取消后是否应恢复库存？  
> 验证方式：记录库存 → 创建占用库存的订单 → 取消 → 查询库存 → 再次取消 → 再查库存。  
> 准备状态：缺少当前测试环境可核对的库存查询能力；保留建议，暂不可执行。

## 5 从推荐到实际检查

```mermaid
flowchart LR
  A[源码索引与按需读取] --> B[带证据的业务概览]
  B --> C[项目特有检查建议]
  C --> D[用户确认关键预期]
  D --> E[项目规则版本]
  E --> F{能力与证据是否具备}
  F -->|具备| G[匹配或生成候选方案]
  F -->|缺条件| H[显示映射 数据或执行器缺口]
  G --> I[独立验证及项目试运行]
  I --> J[人工审核及正式运行]
  J --> K[报告与修复后复测]
```

需要增加“项目规则库”，将确认后的业务预期保存为项目内版本，记录来源片段、用户补充、确认时间与内容指纹。不能只把pendingRules放在报告文本里，也不能把AI输出直接写入全局已验证规则目录。

已有固定规则保留为种子检查和方法参考，例如身份隔离、重复操作、保存一致性，但不限制业务发现的类型或名称。识别出的规则先独立表达业务含义，再判断是否能用现有能力执行。

检查准备状态分为：

1. **已有合格方案可用**：语义和适用条件匹配，核对当前映射与环境后复用。
2. **可生成新方案**：执行动作、观察字段和判定表达式都支持，但仍需生成、验证和审核。
3. **待补条件**：规则明确，缺测试数据、登录角色、接口映射或可观察结果。
4. **待扩展执行能力**：当前执行器、断言或状态处理不能表达；保留建议及说明，不强行套已有规则。

当前create/query/update及有限表达式不能覆盖任意业务。后续HTTP适配器应注册项目操作、请求参数、角色、响应字段和观测来源，能力判定必须检查“如何操作”和“如何证明”，不能只看存在一个HTTP地址。支付外部服务、跨天任务、复杂并发等可以被分析和推荐，但不能因此宣称支持执行。

## 6 避免新规则验证变成自我证明

动态规则扩展还会触及现有独立验证体系。当前固定规则配套的验证样例，不能自动证明一个新业务方案可靠。

新规则至少需要：结构与可执行性检查、断言非空及非恒真的检查、正常场景、已知违反规则场景、证据不足场景，以及目标项目试运行。缺少独立正反例时，方案保持未完成验证，不能使用已有固定规则的通过标签放行。

预期结果来自用户确认的业务规则与可核对资料。AI可协助起草测试数据或样例，但同一次生成的方案和预期答案互相吻合不能当独立证明。按规则选择人工核对、受控缺陷变体或独立实现，并记录独立性边界。初期推荐范围可以宽于正式执行范围，UI应清楚显示两者差异。

## 7 用户操作流程

1. **选择源码项目**：显示识别到的技术栈及允许分析范围，未配置运行环境也可继续。
2. **开始业务分析**：确认模型和发送范围后，显示正在阅读哪个业务入口、已读材料及预算状态。
3. **核对业务概览**：系统先说明“我识别到这些业务”，用户可纠正名称、补充遗漏或选择一条业务深入。
4. **选择推荐检查**：每条显示代码依据、风险理由、预期和可执行状态；按业务组织，不要求用户从固定技术规则名中猜选。
5. **确认关键业务问题**：只询问影响预期结果的缺失或冲突信息，答案保存为项目规则。
6. **准备与验证方案**：可复用则匹配已有方案；需生成则进入现有候选验证支线；能力缺口明确保留。
7. **执行与复测**：沿用现有证据和历史机制，报告标明所选业务、已验证规则、未覆盖建议。

默认展示业务结论、代码依据和缺口摘要；完整阅读日志与原始结构化结果折叠。保留手工选择已有检查的入口，不强制每次运行都重新调用AI。

## 8 与现有模块的关系

| 模块 | 调整 |
| --- | --- |
| `projects/inspect.ts` | 拆出无需启动的源码识别，增加目标文件类型和索引；运行约束留在业务准备层 |
| `model/context.ts` | 从手工文件列表扩展为授权目录内的受限检索与片段读取，保持发送清单与预算；明确项目测试和工具私有答案的分离 |
| `model/provider.ts`与预算 | 保留凭据、连接和审计；增加受控多轮读取任务，记录实际输入及中断状态 |
| `model/proposal.ts` | 输出业务事实、候选预期、风险、证据与缺口，替代只围绕单流程及固定规则的建议 |
| 新项目规则库 | 保存用户确认的新规则及版本，不与全局模板发布混用 |
| `api.ts`及`workflow.ts` | 草稿和执行计划引用项目规则；旧规则ID兼容，不再仅查固定目录 |
| `VerifyView.tsx` | 根据发现的业务与项目规则组织检查，不将新建议全部导回已有固定规则 |
| 执行能力与映射 | 按项目声明动作和观察能力，明确可表达与不可表达的检查 |
| 候选准入及仓颉核心 | 保留现有可信判定链；按明确支持的语义逐步扩展，不能为动态规则跳过独立验证 |
| 经验机制 | 保存用户纠正、规则来源与复测案例，辅助下一次分析；不把旧推断当当前事实 |

## 9 优先顺序与验收

| 步骤 | 交付 | 验收依据 |
| --- | --- | --- |
| A 源码分析与证据 | 只读索引、按需读取、业务概览和阅读范围 | 不提供verification.json也可识别支持语言的主要业务；引用均能回到读过的相应版本源码；能报告未分析范围 |
| B 项目规则与推荐 | 项目特有检查、关键预期确认和能力分级 | 在未写入固定规则目录的业务上给出有依据建议；不把缺陷实现当正确预期；明确不可执行项 |
| C 一条新业务的执行闭环 | 项目规则接入映射、候选、独立验证及复测 | 用一条超出现有固定规则语义、且操作与断言能力可支持的业务证明可执行性；正反例和证据不足样例结果符合预期 |
| D 分析复用与纠错 | 代码变化后更新分析、保存用户纠正 | 旧来源过期能被识别；纠正后不再重复错误推荐；旧报告保持原样 |

具体新业务样例在实施计划阶段选定，先验证所需操作和观察能力再冻结验收案例。命名检查后移，不与此阶段捆绑。未实施前不改变现行需求、候选机制和正式验收状态。

## 10 设计结论

项目主线应调整为“从源码发现业务，形成有依据的检查建议，再把用户确认的规则送入可信执行链”。固定规则成为起步资源；verification.json成为运行配置；源码分析结果、预期规则和执行能力各有独立边界。

方向、设计与实施计划已确认；用户最新允许跳过正式验收继续开发。S1—S5当前开发状态与限制以实施计划及项目规则证据为准；本设计不作为真实模型、人员审核或原生平台验收通过的证据。

## 11 S5开发交付边界（2026-10-14）

读取范围内任何新增、删除或正文变化都会保守失效，包括未引用文件和package/tsconfig等元数据；默认全根范围不豁免新运行配置。若先只分析业务源码再补运行配置，应明确选定src/公开文档范围，运行配置另按实际根目录、源码摘要、映射、数据和账号重新核验。范围外文件不自动转入已确认业务来源。来源根目录不可访问或含链接时只返回历史stale视图，不跟随路径、不复用确认。

纠正只记录在本项目不可变版本历史，追加后清除当前确认和选择；不会自动发给模型或推成跨项目经验。历史报告和v1验证包仍可查看；精确资格、工具、资源或适配缺失时不得复跑。普通打包仍要求真实核心exe，--source-only仅为明确未构建核心的开发交付。私有两套独立资源单独reference-v2包，不进入普通包和发现上下文。详情与实际检查口径见[本阶段证据](../../evidence/discovery-release.md)。
