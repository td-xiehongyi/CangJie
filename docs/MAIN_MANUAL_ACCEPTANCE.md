## 验收顺序与记录方式

建议按 **启动 → 模型设置 → 工单样例主线 → 导出与重开 → 目标负载 → 源码业务分析 → 新规则执行 → 异常恢复 → 交付复现** 顺序操作。先完成一条规则，再增加检查项。

每项记录：日期、验收人、Git提交、项目目录、操作、预期、实际结果、截图/报告路径、项目/分析/候选/运行ID。结论用“通过 / 失败 / 受阻 / 未执行”；不要用“已完成”代替结论。

- **通过**：实际行为符合该项标准，且有证据。
- **失败**：功能行为与标准不符，记录复现步骤。
- **受阻**：缺少模型、原生核心、资源或人员，后续未进入。
- 被测网站发现业务问题可以证明工具检出了问题；不能把该业务写成通过。反过来，模型连接成功也不能证明分析质量合格。

## 1. 确认基线并启动

在 PowerShell 执行：

```powershell

git branch --show-current
git rev-parse --short HEAD
git status --short
node --version
npm --version
Get-Content .\main-version.json
```

**应看到：** 分支为main；记录实际提交；Node为24.x。本轮实际读到Node24.19.0、npm11.17.0。存在未提交证据和output文件是当前基线的一部分，保留原状。

当前主版本配置：端口4317，数据目录 `.local-data/natural-workflow-preview`，方案库为其 `registry` 子目录。不要删除数据、重置仓库或切换到旧8097/8098副本。

1. 如果已运行旧工作台，在其原控制台按Ctrl+C正常停止，确认没有正在执行的任务。
2. 双击根目录 `Start-CangJie.cmd`，观察构建、启动、默认浏览器打开的完整过程。这一项要实际双击一次，终端启动不能替代Shell验收。
3. 若需终端入口，运行 `npm run start:oneclick`。以控制台显示的地址为准，当前默认是 `http://127.0.0.1:4317`。
4. 浏览器未自动打开时可手动访问，并把“自动打开失败、手动可访问”分别记录。

**通过标准：** 构建成功后再启动；四页“项目接入 / 业务验证 / 验证报告 / 模型设置”可访问；原项目与记录仍在；启动本身不自动开始分析或业务运行。网页标签关闭后后台仍运行，Ctrl+C才停止后台。

若缺依赖，先在本目录执行 `npm ci --ignore-scripts`，再启动。缺核心/SDK时按[快速开始](QUICK_START.md)处理；能打开界面和保存设置不代表可以执行候选验证。端口占用时记录提示并关闭确认属于本项目的旧服务，不要把其他服务当作当前main。

## 2. 验收模型设置与重启保存

使用本机页面输入API Key，模型名称填写本轮约定的 `deepseek-flash`，接口地址按实际服务填写。不要把Key写入聊天、截图、报告或Git。

1. 点“保存到本机”。检查成功提示、Key输入框清空；这一步应仅保存，不发起模型连接请求，也不应据此显示本次连接成功。
2. **不勾选记住密钥：** 保存后正常退出后台、重启、刷新页面。地址和模型应保留，Key应需重新输入。
3. **勾选记住密钥：** 重新输入Key后保存，正常退出并以同一Windows用户、同一数据目录重启。应恢复“已提供”状态；不应回显Key。实际凭据恢复能力可在下一步连接检查中验证。
4. 确定愿意向该服务发起请求后，点“保存并检查连接”。它会发起一次最小模型检查，可能计费；记录本次成功或具体错误。此结果不计作源码分析通过。
5. 如果从任务进入设置，点“返回检查方案”或“返回项目分析”，检查项目及原选择保留。

**通过标准：** 两种保存方式符合上述重启行为；保存失败有提示，不静默写明文；本地 `state.json` 只含非秘密配置和凭据引用。查看文件时不要输出可能含秘密的完整内容。

“清除密钥”会删除当前配置对应的凭据。仅在专用验收凭据上测试，随后恢复所需配置；不要为了验收清除现有正式凭据。

## 3. 走通工单样例主线

### 3.1 接入并准备环境

在“项目接入”新建项目，或选择已有工单项目并核对目录：

```text
项目目录：C:\Users\xie\Desktop\Project\samples\ticket
网站用途：合成工单业务人工验收
测试用户：自动生成两个测试用户
```

1. 点“选择文件夹”实际选择一次；再测试取消，能返回页面并手动粘贴路径。
2. 点“检查项目并继续”，选“自行选择检查内容”。本轮先走可执行样例，不需要先做AI分析。
3. 核对独立测试副本与数据复位条件，勾选同意，执行准备；按实际页面按钮继续。
4. 看到两个测试用户登录成功后，点“继续选择检查”。

**通过标准：** 目录和用途明确，环境准备有进度及结果，测试账号仅在独立副本创建；缺初始化或映射时列出缺口，不能伪装成准备成功。此路径与“读取源码并分析业务”是两种入口。

### 3.2 选择规则

在“业务验证”，先选择“新增工单”，只勾选“提交结果保存”，再勾选“这就是我期望的网站行为”。

**通过标准：** 选择能保存，刷新后仍可核对；规则定义可展开，页面显示本轮判定/仅观察数量。如果已有合格方案，查看其适用条件与固定版本，然后转3.5执行；这只验已有方案复用，不能算真实候选生成验收。

### 3.3 缺方案时生成并自动验证

1. 点“为这条规则创建检查方案”。若已有方案且需要专门验生成，在“检查方案与版本”内使用“重新生成检查方案”。
2. 如出现“创建方案前准备”，核对服务地址、发送文件和过滤后内容，明确同意后点“确认范围并创建方案”。源码分析同意与候选生成同意要按各自页面核对。
3. 等待生成、独立自动验证、项目试运行；查看阶段、具体错误及已有证据，避免重复创建任务。

**通过标准：** 只有独立准入和项目试运行达到要求后才能进入审核；未知结果或缺独立资源时保留待处理/受阻，不能直接发布。记录这次实际模型、候选ID、修订次数和结果。模型生成失败或预算耗尽按实际记录，不改成测试服务凑通过。

### 3.4 保存材料并完成实际审核

1. 在本页“检查方案验证与审核”展开定义、正反例、端到端和项目试运行证据。
2. 核对或填写“适用条件 / 排除条件 / 使用说明”，再点“保存本版审核材料”。AI预填的“AI参考，待确认”必须人工核对。
3. 业务确认人核对正确预期和适用范围；开发者技术审核人核对独立对照、取证和限制。填写实际审核身份，并分别勾选两项确认。
4. 点“审核通过，保存为可复用方案”，记录固定版本与摘要。

**通过标准：** 未保存说明、缺任一审核或身份时不能发布；修改说明后旧确认失效，必须重新保存及审核。只进入本机方案库；不能用测试人名代替实际审核。缺审核人就记录受阻。

### 3.5 执行业务检查并查看证据

1. 重新核对所选规则和方案版本，点“准备本轮检查”。
2. 在“本轮运行准备”确认环境，点“开始检查”。
3. 等待完成，点“查看检查结果”。
4. 逐项查看预期/实际、判定依据、请求与观察、证据引用及方案版本。完成一条后，再增加“重复提交不重复创建”和“账号之间权限隔离”；标题检查使用“修改工单标题（其他字段不变）”操作，单独运行。

**通过标准：** 有新的真实运行ID，项目/主流程/规则/固定版本一致；HTTP成功不是唯一依据，保存、重复性、身份隔离和字段保持分别有证据。无证据或未知不能判通过。运行完成也不等于所有业务断言通过。

## 4. 导出、重开与无模型复跑

1. 在报告“导出、复测与运行详情”中点“下载 Markdown”和“导出验证包”，实际打开下载文件，核对运行ID、规则版本、证据和限制。
2. 记录旧报告摘要；正常退出后台，重新启动并刷新，确认旧报告与已发布方案仍可查。
3. 在“验证报告”点“加载验证包”，选择刚下载的JSON，先核对包的项目、流程和版本。加载/查看不应自动执行或调用模型。
4. 在“复跑准备”重新准备自动测试账号；手动模式需重新输入本次密码，再点“开始检查”。可用未保存Key的会话验证无模型复跑，不必清除现有凭据。
5. 检查产生新运行、关联原运行；旧报告和证据保持，新结果按这次实际执行判定。

**通过标准：** 复跑需要真实执行条件和精确版本，不能仅重显旧通过结果；缺核心/资源/适配或来源失效时明确阻断。源码或映射改变后，先重新接入并确认新条件，报告必须体现条件变化，不能声称原条件重跑。

## 5. 验收目标负载

只从**所选规则全部已确认、实际业务断言全部通过**的报告进入“目标负载”。存在失败、未知、仅观察或未完成时应不能开始。

1. 展开“设置并开始负载检查”，先选“记录运行表现”。可先用每秒1次、持续8秒、单规则100%做操作冒烟；多规则可点“均分占比”。这些只是验收起步值，不是实际业务容量目标。
2. 核对目标、比例和资源上限，勾选确认，点“开始目标负载验证”。
3. 检查低负载预检、运行、结算、停止原因；下载负载报告与账本证据。“记录运行表现”不能输出目标达标结论。
4. 再选“验证目标是否达标”，由业务方填写实际等待上限、允许错误百分比与目标次数/时长；没有约定阈值时把正式达标验收记为未执行。
5. 另起一轮较长运行，点击“停止派发并结算”，检查在途结果有限结算并保留停止原因。

**通过标准：** 占比合计100%；缺阈值不能开始达标判定；报告绑定来源运行/版本/环境，呈现派发、完成、P95、错误、未知及压测端丢弃。执行端受限或未结算不能判达标。单位为“完整业务检查/秒”，不能当作裸HTTP RPS或线上最大容量。本项需要真实k6。

## 6. 验收源码业务分析与推荐质量

建议从 `samples\status-ticket` 开始；另用 `tests\fixtures\discovery-orders` 和 `tests\fixtures\discovery-memberships` 检查不同业务的推荐。后两者用于源码理解，不能因有分析建议就视为已具备运行配置。

1. 在“项目接入”选目录，点“读取源码并分析业务”。只应索引并进入分析准备，不应立即外发或启动网站。
2. 点“查看读取与发送范围”，核对模型服务、允许目录、排除路径、文件摘要和预算。正文只能在同意范围内按需发送；涉及项目自身测试时明确选择。
3. 明确同意外发后勾选授权，点“开始源码业务分析”。分析期间保持源码不变。
4. 展开实际源码引用，将路径、行号和片段与本地文件逐项对照；查看实际已读片段及未读文件。
5. 逐项核对业务对象、角色、流程和建议：工单关闭应涉及关闭后拒绝重开、标题及归属保持；订单建议应对应取消权限/未支付条件/库存只释放一次；会员建议以该目录公开说明与实现为准，先由人工写下正确预期再比较模型输出。
6. 可点“聚焦这条业务”，检查它仍是待确认建议；不会自动变成已执行或已通过规则。

**通过标准：** 事实有有效源码引用，文档/测试中的候选预期与AI假设分开；读取局限和未决问题明确；建议与实际业务相关。完成分析不等于完整理解，漏读关键材料必须如实记录。若分析暂停，检查具体原因并尝试“继续原分析”，预算不能清零。

## 7. 验收规则版本与受控新规则执行

先完成第6步工单关闭分析。建议在独立样例副本上做版本、来源变化与停用测试；保留主版本已有项目和正式方案。副本可由文件管理器复制样例到新建验收目录，记录绝对路径，不覆盖原目录，也不要复制工具私有验收答案。

1. 在“核对业务预期”回答关键问题，核对三项公开约定：允许open→closed；closed后请求open必须拒绝且仍为closed；标题与归属在每次转换后保持。
2. 只有这些约定确实符合所验业务时，勾选“采用受控工单关闭契约”，确认并保存项目规则。其他业务不能为绕过缺能力而套用该契约。
3. 记录规则ID、v1、内容摘要和来源；点“选择此版本（仅保存草稿）”。应显示准备状态，保存/选择本身不执行。
4. 如最初仅接入源码，点“接入运行配置（保留分析）”，使用**同一源码目录**的status-ticket配置完成环境准备；回查原分析及规则仍保留。
5. 在“业务验证”点“编译此精确规则版本”。只有当前已确认且来源有效的版本可编译。
6. 在下方选择编译后的项目规则并确认预期，按3.3—3.5生成、独立验证、试运行、实际双重审核及业务运行，再按第4步导出复跑。
7. 回到规则库点“修订业务预期”，填写纠正说明并保存：应新增v2、清除确认，不改v1。查看历史版本，核对旧报告仍引用当时精确版本。新版本需重新确认、选择及编译，不能自动沿用v1资格。
8. 对没有对应执行能力的真实建议，保存自由文本预期并尝试编译；应明确显示“缺少执行能力/测试条件”等缺口，不能把“规则已保存”当作可执行。

**通过标准：** 四种准备状态“已有合格方案 / 可生成方案 / 缺少测试条件 / 缺少执行能力”含义清楚；新规则执行受精确版本、映射、独立资源和来源校验约束。当前仅支持已审查的工单关闭语义，不能据此宣称任意自由文本或网站可执行。

## 8. 异常恢复与界面补充检查

以下使用专用验收项目/方案。每项独立操作，记录失败画面和恢复结果。

| 场景 | 操作 | 应有结果 |
| --- | --- | --- |
| 源码范围变化 | 对已分析副本的授权业务范围新增/修改文件，再查看、确认或执行 | 观测到变化后显示来源失效；旧记录可看，当前确认/选择/执行受阻；重新索引并新建分析。不是保证文件变化瞬间停止所有已发请求 |
| 修订或纠正 | 追加“处理/纠正记录” | 追加待确认版本、清除选择，不改历史、不恢复旧方案资格 |
| 暂停分析 | 运行中点“暂停分析”，再“继续原分析” | 保留任务、已读证据和累计预算；不隐式创建全新预算 |
| 两个页面冲突 | 同项目双标签分别修改检查选择 | 说明冲突；允许明确选择保留本页重新保存或加载已保存选择，不静默覆盖 |
| 未保存说明 | 编辑审核材料后切页或刷新 | 有离开保护，保存/放弃含义明确；不自动审核或发布 |
| 会话失效 | 已保存工作后正常重启后台，旧页尝试保存 | 提示重连；输入尽可能保留，重连后需手动重试，不偷偷重发审核 |
| 业务停止 | 运行中点“停止本轮运行” | 保留已收集证据及停止状态，不误写全部通过 |
| 方案停用 | 在报告的“方案维护：停用版本”中，仅停用专用验收版并填写原因 | 旧报告保持，后续使用该精确版受阻；不自动替换其他版 |
| 无效包 | 加载损坏JSON、未知版本包 | 有错误提示，不运行、不覆盖历史 |
| 窄屏与键盘 | Edge调为390/768宽，再用Tab操作核心控件 | 导航、长路径、错误与下一步可辨认；关键按钮可到达、焦点可见，无影响操作的横向溢出 |

## 9. 正式交付另验

若验收目标包含交付，使用本次main重新构建后产生的**新目录**，按[交付指南](delivery-guide.md)执行：

1. 记录源码提交、构建结果及交付清单；普通运行包要求真实原生核心。source-only包不能代替正式运行包。
2. 在安装依赖或资源前核对原始交付文件摘要；选择全新中文/空格目录，不复制开发数据、凭据、旧报告或数据库。
3. 分别安装依赖与独立开发者验收资源；私有资源不进入模型发送范围。缺资源时应提示 `VALIDATION_RESOURCES_REQUIRED`。
4. 从空配置完成启动、真实模型、实际审核、业务检查、导出、正常重开及复跑。
5. 本机新目录复现与另一电脑兼容性分开记录；T10同模型两组价值对照按其专门方案另验。

旧ZIP不会因main更新而更新。本项未执行时，交付继续保持未验收。

## 验收记录模板与结束条件

将以下模板复制到单独的验收记录，替换占位符，不覆盖既有证据：

```text
日期 / 验收人：
源码：main@<实际提交>；工作区改动：<记录>
Node / npm / Windows / 浏览器 / 核心 / k6：
主版本标识 / 地址 / 数据目录：
被测项目绝对路径 / 来源摘要：
模型服务 / 模型名（不含Key）：
步骤编号 / 操作：
预期：
实际：
结论：通过 / 失败 / 受阻 / 未执行
项目 / 分析 / 规则版本 / 候选 / 运行 / 负载ID：
截图 / Markdown / 验证包 / 账本路径：
未覆盖范围 / 下一步：
```

只有实际执行、有证据的范围才能勾选通过：

- [ ] Windows双击、默认浏览器与当前main启动。
- [ ] 本地保存、两种Key策略及正常重启。
- [ ] 工单接入、真实候选、独立验证和实际双重审核。
- [ ] 业务判定、证据导出与重开无模型复跑。
- [ ] 负载记录、正式目标判定与停止结算。
- [ ] 真实源码分析质量、引用与局限。
- [ ] 精确规则版本、受控新规则执行及缺能力阻断。
- [ ] 来源变化、纠正、冲突、会话和停用保护。
- [ ] 本次main的新交付目录复现（目标包含交付时）。

一条路径通过只说明该项目、规则、版本和环境的结果。真实模型效果、实际审核、交付或T10仍有未验事项时，项目保持Active。
