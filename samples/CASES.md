# 三个样例的正反例与证据不足案例

本轮只覆盖工单提交、活动报名、工单状态三个既有业务。原样例保持正常实现，缺陷由脚本复制到独立练习目录后注入。

## 生成与导入

在仓库根目录执行：

```powershell
npm run samples:case -- --list
npm run samples:case -- --case ticket-field-change
```

命令输出 `project` 的完整路径。在 鉴实 中只导入该 `project` 子目录，再按正常步骤确认业务、运行条件和检查方案。每次生成新目录，不覆盖旧副本。也可用 `--out <尚不存在的目录>` 指定位置，其父目录须已存在；放到仓库外独立演示时须自行准备该样例依赖。

同级 `case.json` 和 README 用于人工对照，包含预期标签，不属于被测项目源码。它们不是实际运行结果，也不能替代独立验证器的可信对照。所有案例是公开练习材料，不能当作留出评测集。

## 核对步骤

### 工单提交与活动报名

1. 以创建者登录，提交标题／姓名，随后重新查询，核对保存的内容。
2. 同一批次、同一提交意图重试，完整查询应只含一条对应记录；新提交意图允许创建新记录。
3. 切换另一个账号，在相同批次查询，不能看到创建者记录；尝试修改也应被拒绝。
4. 创建者只修改标题／姓名，分别核对修改前、修改后的内容、优先级／组别、归属。
5. 报名的 creatorId 是回执访问身份，ownerId 是业务归属；二者分别核对。

### 工单状态

1. 创建 open 工单并查询原始标题、归属、状态。
2. 关闭并立即查询，状态应为 closed，标题和归属均保持。
3. 尝试重开应被拒绝，再查询状态仍为 closed、标题和归属仍保持。
4. 反例 temporary-mutation 在第2步改错标题、第3步恢复；只比较首尾会漏检。
5. 非法操作正确被拒绝是正例；必须核对拒绝后的真实状态，单看409响应不够。

## 证据不足如何处理

三个 incomplete-query 案例都保留可见数据，但明确将查询完整性标记为 false。即使局部值吻合，也不能证明所选业务通过；缺少完整查询不能直接当作业务缺陷。

其他需要保留“无法判断”的条件：没有后续查询、缺少修改前基线、第二账号身份未验证、映射字段缺失、查询超时。它们不是本轮新增业务；相应条件需通过现有运行／映射检查补齐。

## 结果差异展示

结果页对失败与证据不足项直接显示“操作前 → 预期 → 操作后／实际观察”；通过项折叠在“查看通过项的结果对照”。字段保持采用实际操作前值；指定参数检查注明操作前不适用。

每条对照保留断言、具体字段来源、证据引用和原始观察。缺失或存在歧义的观察显示“未取得”，不会用后续恢复值替换中间错误值，不会自行改写判定。仅观察记录不显示通过／失败的对照。复测对比和复制问题说明使用相同对照值。
